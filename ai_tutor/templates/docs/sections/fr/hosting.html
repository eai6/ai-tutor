Trois parcours pris en charge pour une installation sur serveur, plus deux formats hors ligne. Tous exécutent la même application ; ils diffèrent par la personne qui exploite la machine en dessous et par la quantité de plomberie fournie déjà montée. Ce qui suit est le détail opérationnel — le manuel d'hébergement autonome accompagne l'application et fait foi si les deux venaient à diverger.

  • Choisissez A si vous disposez d'un serveur ou d'une exigence de centre de données, ou si vous voulez tout le système à l'intérieur d'une machine que vous pouvez désigner du doigt. C'est le plus simple à comprendre et le moins cher à exploiter.
  • Choisissez B si vous êtes déjà sur AWS, s'il faut que le service survive à la panne d'une machine sans intervention humaine, ou si vous prévoyez de dépasser un seul serveur.
  • Ne choisissez C que si vous ne pouvez pas exécuter de conteneurs — une politique qui interdit Docker, ou un parc Python géré dans lequel il faut s'insérer. Vous installez la même application depuis un paquet wheel, mais la base de données, le TLS et la supervision des processus que le parcours A vous livre en une commande deviennent tous votre responsabilité.

Aucun d'eux ne change ce que fait le tuteur, ni l'endroit où le modèle s'exécute. Cela, c'est la section 5.

Parcours A — un serveur

Trois conteneurs, deux volumes, un serveur. La base de connaissances est stockée sous forme de vecteurs à l'intérieur de Postgres, il n'y a donc pas de base vectorielle distincte à exploiter.

        Internet
            │
          Caddy            le TLS se termine ici ; le certificat est
            │              obtenu et renouvelé automatiquement
            ▼
     Django + Gunicorn  ── volume media (figures téléversées)
            │
            ▼
   PostgreSQL + pgvector ── volume de données

Ce qu'il vous faut

  • Un serveur Linux : 4 vCPU, 8 Go de RAM, 60 Go de disque. Fonctionne sur x86-64 comme sur ARM. Un VPS de 2 Go ne suffira pas — l'image pèse environ 7 Go, avec une version CPU de PyTorch, un modèle de reconnaissance vocale et une voix.
  • Si vous construisez au lieu de télécharger, prévoyez 25 Go libres : le cache de couches est nettement plus gros que le résultat.
  • Docker et le greffon Compose.
  • Un nom de domaine pointant vers l'IP publique du serveur, ports 80 et 443 joignables. Sans cela, impossible d'émettre du HTTPS.
  • Au moins une clé d'API de fournisseur de modèle — ou aucune, si vous utilisez le modèle local intégré décrit ci-dessous.

Installer

Il vous faut cinq fichiers : la définition compose, la configuration TLS, un modèle de configuration, et les scripts de sauvegarde et de restauration. Extrayez-les de l'image publiée — pas de code source, pas d'accès au dépôt, et ils ne peuvent pas se désynchroniser de l'image qu'ils configurent.

mkdir -p ai-tutor && cd ai-tutor

docker run --rm ghcr.io/eai6/ai-tutor:latest \
  tar -C /app/deploy/compose -c \
      docker-compose.yml Caddyfile env.example backup.sh restore.sh | tar -x

cp env.example .env
chmod 600 .env

Ouvrez le .env et renseignez tout ce qui est marqué REQUIRED ; chaque entrée indique ce qu'elle est et ce qui casse en son absence. Générez les deux secrets plutôt que de les inventer :

python3 -c "import secrets; print(secrets.token_urlsafe(64))"   # SECRET_KEY
python3 -c "import secrets; print(secrets.token_urlsafe(32))"   # POSTGRES_PASSWORD

Puis récupérez l'image et démarrez :

docker compose pull        # ~7 Go, une seule fois
docker compose up -d
docker compose logs -f app

FAITES PULL AVANT UP

Si l'image n'est pas déjà sur la machine, docker compose up la construit depuis le source — ce qui exige le code source, environ 25 Go de disque libre et beaucoup de temps. L'image publiée est en x86-64 ; sur un serveur ARM, clonez le dépôt et lancez docker compose build, qui est aussi la façon de produire une image ARM. Rien n'est lié à une architecture.

Démarrer sans aucun compte fournisseur

docker compose --profile local-llm up -d

Cela ajoute un conteneur avec un modèle local, télécharge un modèle d'environ 2,6 Go au premier démarrage et y dirige le tuteur automatiquement. Voyez-le comme un moyen de commencer sans compte commercial, non comme un équivalent : un petit modèle local enseigne de façon mesurablement moins bonne, réclame environ 4 Go de RAM en plus de l'application, et est plus lent sur un serveur sans GPU. Ajoutez plus tard une clé de fournisseur et redémarrez — la configuration locale s'efface d'elle-même.

Ce que vous obtenez au premier démarrage

L'image contient déjà un programme chargé — cours, leçons, étapes et tickets de sortie — importé au tout premier démarrage du conteneur. Rien n'est téléchargé, un premier essai fonctionne donc sans aucune connexion Internet.

Les figures et les images ne sont pas incluses. Elles pèsent environ vingt fois le texte. Près des trois quarts des étapes de leçon renvoient à une figure ; ces étapes présenteront donc un vide visible jusqu'à ce que vous ajoutiez des médias — en téléversant les vôtres depuis le tableau de bord enseignant, ou en important un pack construit avec les médias :

# sur une installation qui possède les figures
python manage.py build_curriculum_pack --institution <id> --out dist/

# puis sur celle-ci
docker compose exec app python manage.py import_curriculum_pack /path/pack.tar.gz --force

Le premier démarrage prend plusieurs minutes : migrations, données de référence et index d'aide. C'est prêt quand le journal montre gunicorn à l'écoute et que docker compose ps affiche app healthy. S'il manque une valeur obligatoire, Compose refuse de démarrer et indique laquelle — un serveur à moitié configuré est pire qu'un serveur qui n'a pas démarré.

Première utilisation

  1. Créez le compte administrateur : docker compose exec app python manage.py createsuperuser
  2. Connectez-vous à https://<votre-domaine>/admin/ et indiquez quel modèle sert quelle finalité dans LLM → Model configs. Rien ne fonctionne tant qu'au minimum le tutorat ne pointe pas vers un fournisseur dont vous avez fourni la clé.
  3. Créez l'établissement et téléversez un programme depuis le tableau de bord enseignant.
  4. Faites un tour de tutorat. C'est le vrai test — il sollicite la base de données, la base de connaissances, les identifiants et les médias en une seule action. Un contrôle de santé ne le fait pas.

Mettre à jour

cd ai-tutor
docker compose pull
docker compose up -d

Les migrations s'exécutent automatiquement au démarrage. Sauvegardez d'abord. Pour figer une version au lieu de suivre la dernière, définissez IMAGE_TAG=v1.2.0 dans le .env — figer fait de la mise à jour une décision, et du retour arrière une ligne à changer.

Parcours B — votre propre compte AWS

DNS et un pare-feu en façade, un répartiteur de charge qui termine le TLS, l'application sur Fargate dans des sous-réseaux privés sans adresse publique, un Postgres géré à côté, et un accès Internet sortant uniquement via une passerelle NAT. Le coût de cette configuration figure en section 6.

Ce qu'il vous faut d'abord

  • Un compte AWS et un rôle capable de créer des ressources VPC, ECS, RDS, S3, IAM, WAF et Route 53.
  • Un domaine que vous contrôlez — on ne peut pas émettre de certificat pour le nom d'hôte d'un répartiteur de charge appartenant à AWS.
  • Au moins une clé d'API de fournisseur de modèle.
  • Installés localement : git, aws CLI v2, pulumi, docker, Python 3.12.
  • Le dépôt, pour le programme d'infrastructure-as-code dans infra/aws/. Le parcours A peut fonctionner à partir de la seule image publiée ; celui-ci non.

Étape 1 — Cloner et configurer la stack

git clone <repo> ai-tutor && cd ai-tutor/infra/aws
python -m venv venv && ./venv/bin/pip install -r requirements.txt

aws configure                 # ou aws sso login
pulumi login --local          # état dans ~/.pulumi ; sauvegardez-le
pulumi stack init prod

pulumi config set aws:region eu-west-1
pulumi config set aitutor-aws:db-instance-class db.t4g.medium
pulumi config set aitutor-aws:db-storage-gb 50
pulumi config set aitutor-aws:min-tasks 1
pulumi config set aitutor-aws:max-tasks 4

# Définissez vous-même le mot de passe de la base — ne le laissez PAS être généré
pulumi config set --secret aitutor-aws:db-password "<un long mot de passe aléatoire>"
pulumi config set --secret aitutor-aws:django-secret-key "<50+ caractères aléatoires>"
pulumi config set --secret aitutor-aws:anthropic-api-key "sk-ant-..."

Étape 2 — Monter l'infrastructure

pulumi up                                        # examinez le plan, puis confirmez
pulumi config set aitutor-aws:enable-ecs true    # puis ajoutez le service
pulumi up

Le service est délibérément derrière ce second commutateur, afin que la fondation puisse être vérifiée avant que quoi que ce soit ne tourne dessus.

Étape 3 — Domaine et HTTPS

pulumi config set aitutor-aws:domain-name tutor.education.gov.xx
pulumi config set aitutor-aws:hosted-zone-id Z0123456789ABCDEFGHIJ
pulumi up

Pulumi demande le certificat, écrit l'enregistrement de validation, attend l'émission, ajoute l'écouteur HTTPS et redirige le port 80. Attendez-vous à une attente pendant la validation ; en cas de dépassement de délai, rien n'a changé et le site est toujours servi sur le port 80.

LAISSEZ L'OUTILLAGE POSSÉDER L'ENREGISTREMENT DE VALIDATION

Le certificat est revalidé au renouvellement à l'aide de cet enregistrement DNS. Un enregistrement ajouté à la main que quelqu'un range plus tard casse le renouvellement environ onze mois après — bien après que quiconque puisse relier les deux événements.

Étape 4 — Construire et déployer l'image applicative

aws ecr get-login-password | docker login --username AWS \
  --password-stdin <acct>.dkr.ecr.<region>.amazonaws.com
docker build --platform linux/amd64 -t <ecr-url>:v1 .   # amd64 compte sur Apple Silicon
docker push <ecr-url>:v1
pulumi config set aitutor-aws:image-tag v1 && pulumi up

./ops/migrate_and_seed.sh                               # tâche ponctuelle

Ou poussez sur la branche main de votre fork et laissez le workflow de déploiement s'en charger. Ici, les migrations doivent être une tâche ponctuelle, pas une partie du démarrage du conteneur : le service lance toutes les tâches en même temps, des migrations dans la commande de démarrage entreraient donc en concurrence entre réplicas.

Étapes 5 et 6 — Pare-feu, puis vérification

Le pare-feu démarre en mode comptage, pour que vous puissiez voir ce qu'il bloquerait avant qu'il ne bloque quoi que ce soit de réel. Activez-le, puis vérifiez comme vous le feriez sur n'importe quel parcours :

pulumi config set aitutor-aws:waf-block-mode true && pulumi up

curl -s https://tutor.education.gov.xx/health/     # {"status": "ok", ...}

Chargez ensuite le site, créez un compte personnel, téléversez un programme et faites un tour de tutorat.

Parcours C — installation par pip, sans Docker

La même application installée comme paquet Python, pour un parc où les conteneurs sont exclus.

Ce qu'il vous faut d'abord

  • Un serveur Linux : 4 vCPU, 8 Go de RAM, 60 Go de disque.
  • Python 3.12 ou plus récent — la version du framework l'exige.
  • PostgreSQL 14+ avec l'extension pgvector disponible. L'extension est créée par une migration ; elle doit seulement être disponible, pas activée à la main.
  • Un domaine pointant vers le serveur, et de quoi terminer le TLS.
  • Environ 3 Go de disque rien que pour les dépendances.
sudo apt install python3.12 python3.12-venv postgresql postgresql-16-pgvector
sudo -u postgres createuser --pwprompt aitutor
sudo -u postgres createdb --owner aitutor aitutor

sudo python3.12 -m venv /opt/ai-tutor/venv
sudo /opt/ai-tutor/venv/bin/pip install ai-tutor

sudo /opt/ai-tutor/venv/bin/ai-tutor init      # écrit /etc/ai-tutor/ai-tutor.env (0600)

init génère une clé de signature et crée le répertoire de données. Le relancer n'écrase jamais un fichier existant — faire tourner la clé déconnecterait tous les utilisateurs et invaliderait tous les liens de réinitialisation de mot de passe en cours. Éditez ce fichier et renseignez ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS (avec le schéma), DATABASE_URL et au moins une clé de fournisseur.

sudo /opt/ai-tutor/venv/bin/ai-tutor migrate
sudo /opt/ai-tutor/venv/bin/ai-tutor seed
sudo /opt/ai-tutor/venv/bin/ai-tutor collectstatic --noinput
sudo /opt/ai-tutor/venv/bin/ai-tutor createsuperuser

sudo /opt/ai-tutor/venv/bin/ai-tutor systemd | sudo tee /etc/systemd/system/ai-tutor.service
sudo systemctl daemon-reload && sudo systemctl enable --now ai-tutor

L'unité générée porte les vrais chemins de cette installation, redémarre en cas d'échec et confine les écritures au répertoire de données. Elle écoute sur 0.0.0.0:8000 avec un délai de 300 secondes — long, parce qu'un tour de tutorat prend de 20 à 90 secondes et qu'un délai plus court tue le worker en pleine réponse. Tout proxy que vous placez devant doit sonder /health/ en HTTP simple et transmettre X-Forwarded-Proto ; /health/ est exempté de la redirection HTTPS précisément pour cette raison. Avec nginx, mettez proxy_read_timeout 300s; — la valeur par défaut de 60 secondes coupe les réponses longues au milieu d'une phrase.

CE QUE CE PARCOURS NE VOUS DONNE PAS

La base de données — installer, régler, sécuriser et sauvegarder Postgres est à vous, et rien ici ne crée de calendrier de sauvegarde. Le TLS — aucun certificat n'est obtenu ni renouvelé pour vous. L'isolement — l'application tourne comme un processus ordinaire, pas dans un conteneur. Et notez que laisser l'URL de base de données non définie bascule sur une base fichier dans le répertoire de données : praticable pour une petite école, mais pgvector n'y est pas disponible, de sorte que la recherche dans la base de connaissances se dégrade en un balayage exact plus lent, qui ne tiendra pas à l'échelle d'une école entière.

La mise à jour est manuelle sur ce parcours, et c'est celle qu'on rate le plus souvent : pip remplace le code et ne redémarre rien.

sudo /opt/ai-tutor/venv/bin/pip install --upgrade ai-tutor
sudo /opt/ai-tutor/venv/bin/ai-tutor migrate
sudo /opt/ai-tutor/venv/bin/ai-tutor collectstatic --noinput
sudo systemctl restart ai-tutor

Sauvegarde et restauration

ParcoursComment
ALes scripts accompagnent le fichier compose : ./backup.sh → ./backups/aitutor-AAAA-MM-JJ-HHMM.tar.gz, et ./restore.sh backups/<fichier>.tar.gz pour le remettre. L'archive contient la base de données et les médias téléversés, pris ensemble.

La base de données contient la référence de chaque figure et le volume contient le fichier : c'est pourquoi les deux sont pris ensemble. Une base restaurée face à des médias plus anciens laisse des leçons aux images cassées et ne signale aucune erreur.

TROIS RÈGLES VALABLES POUR TOUS LES PARCOURS

Une sauvegarde qui n'existe que sur la machine qu'elle sauvegarde n'est pas une sauvegarde. Les sauvegardes contiennent des dossiers d'élèves — conservez-les chiffrées, avec un accès restreint aux mêmes personnes qui peuvent atteindre le serveur. Et testez une restauration : une sauvegarde non testée est une supposition, faites-le donc une fois sur une machine de rechange avant d'en avoir besoin.
