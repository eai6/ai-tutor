Three supported paths for a server deployment, plus two offline shapes. All of them run the same application; they differ in who operates the machine underneath it and how much of the surrounding plumbing arrives with it. What follows is the operative detail — the self-hosting manual ships with the application and stays authoritative if the two ever disagree.

  • Choose A if you have a server or a data-centre requirement, or you want the whole system inside one machine you can point at. It is the simpler thing to understand and the cheaper thing to run.
  • Choose B if you already operate in AWS, need it to survive a machine failure without anyone intervening, or expect to grow past one server.
  • Choose C only if you cannot run containers — a policy that forbids Docker, or a managed Python estate you have to fit into. It installs the same application from a wheel, but the database, TLS and process supervision that Path A hands you in one command all become yours to assemble.

None of them changes what the tutor does, or where the model runs. That is section 5.

Path A — one server

Three containers, two volumes, one server. The knowledge base is stored as vectors inside Postgres, so there is no separate vector database to run.

        Internet
            │
          Caddy            TLS terminates here; the certificate is
            │              obtained and renewed automatically
            ▼
     Django + Gunicorn  ── media volume (uploaded figures)
            │
            ▼
   PostgreSQL + pgvector ── data volume

What you need

  • A Linux server: 4 vCPU, 8 GB RAM, 60 GB disk. x86-64 or ARM both work. A 2 GB VPS will not run this — the image is about 7 GB, carrying a CPU build of PyTorch, a speech recognition model and a voice.
  • If you build rather than pull, budget 25 GB free: the layer cache is comfortably larger than the result.
  • Docker and the Compose plugin.
  • A domain name pointing at the server's public IP, with ports 80 and 443 reachable. HTTPS cannot be issued without it.
  • At least one model provider API key — or none, if you use the bundled local model below.

Install

You need five files: the compose definition, the TLS configuration, a configuration template and the backup and restore scripts. Take them out of the published image — no source code, no repository access, and they cannot be a version out of step with the image they configure.

mkdir -p ai-tutor && cd ai-tutor

docker run --rm ghcr.io/eai6/ai-tutor:latest \
  tar -C /app/deploy/compose -c \
      docker-compose.yml Caddyfile env.example backup.sh restore.sh | tar -x

cp env.example .env
chmod 600 .env

Open .env and fill in everything marked REQUIRED; each entry says what it is and what breaks without it. Generate the two secrets rather than inventing them:

python3 -c "import secrets; print(secrets.token_urlsafe(64))"   # SECRET_KEY
python3 -c "import secrets; print(secrets.token_urlsafe(32))"   # POSTGRES_PASSWORD

Then pull the image and start:

docker compose pull        # ~7 GB, once
docker compose up -d
docker compose logs -f app

PULL BEFORE UP

If the image is not already on the machine, docker compose up builds it from source instead — which needs the source, about 25 GB of free disk and a good deal of time. The published image is x86-64; on an ARM server, clone the repository and run docker compose build, which is also how an ARM image gets made. Nothing is pinned to an architecture.

Starting with no provider account at all

docker compose --profile local-llm up -d

That adds a local model container, pulls a ~2.6 GB model on first start and points the tutor at it automatically. Treat it as a way to get started without a commercial account, not as an equivalent: a small local model is measurably weaker at tutoring, needs roughly 4 GB of RAM beyond the application, and is slower on a server with no GPU. Add a provider key later and restart — the local configuration steps aside on its own.

What you get on first start

The image ships with a curriculum already loaded — courses, lessons, steps and exit tickets — imported the first time the container boots. Nothing is downloaded, so a first run works with no internet at all.

Figures and images are not included. They are roughly twenty times the size of the text. About three quarters of lesson steps reference a figure, so those steps read with a visible gap until you add media — by uploading your own through the teacher dashboard, or by importing a pack built with media:

# on a deployment that has the figures
python manage.py build_curriculum_pack --institution <id> --out dist/

# then, on this one
docker compose exec app python manage.py import_curriculum_pack /path/pack.tar.gz --force

First start takes several minutes: migrations, reference data and the help index. It is ready when the log shows gunicorn listening and docker compose ps reports app healthy. If a required value is missing, Compose refuses to start and names it — a half-configured server is worse than one that did not start.

First run

  1. Create the administrator account: docker compose exec app python manage.py createsuperuser
  2. Sign in at https://<your-domain>/admin/ and set which model serves which purpose under LLM → Model configs. Nothing works until at least tutoring points at a provider whose key you supplied.
  3. Create the institution and upload a curriculum through the teacher dashboard.
  4. Take one tutoring turn. This is the real test — it exercises the database, the knowledge base, the credentials and media in one action. A health check does not.

Upgrading

cd ai-tutor
docker compose pull
docker compose up -d

Migrations run automatically on start. Take a backup first. To pin a version rather than track latest, set IMAGE_TAG=v1.2.0 in .env — pinning makes an upgrade something you choose, and a rollback a matter of changing one line.

Path B — your own AWS account

DNS and a firewall in front, a load balancer terminating TLS, the application on Fargate in private subnets with no public address, a managed Postgres beside it, and outbound-only internet through a NAT gateway. The cost of this shape is in section 6.

What you need first

  • An AWS account, and a role that can create VPC, ECS, RDS, S3, IAM, WAF and Route 53 resources.
  • A domain you control — a certificate cannot be issued for an AWS-owned load balancer hostname.
  • At least one model provider API key.
  • Installed locally: git, aws CLI v2, pulumi, docker, Python 3.12.
  • The repository, for the infrastructure-as-code program in infra/aws/. Path A can run from the published image alone; this path cannot.

Step 1 — Clone and configure the stack

git clone <repo> ai-tutor && cd ai-tutor/infra/aws
python -m venv venv && ./venv/bin/pip install -r requirements.txt

aws configure                 # or aws sso login
pulumi login --local          # state in ~/.pulumi; back this up
pulumi stack init prod

pulumi config set aws:region eu-west-1
pulumi config set aitutor-aws:db-instance-class db.t4g.medium
pulumi config set aitutor-aws:db-storage-gb 50
pulumi config set aitutor-aws:min-tasks 1
pulumi config set aitutor-aws:max-tasks 4

# Set the database password yourself — do NOT let it be generated
pulumi config set --secret aitutor-aws:db-password "<a long random password>"
pulumi config set --secret aitutor-aws:django-secret-key "<50+ random chars>"
pulumi config set --secret aitutor-aws:anthropic-api-key "sk-ant-..."

Step 2 — Bring up the infrastructure

pulumi up                                        # review the plan, then confirm
pulumi config set aitutor-aws:enable-ecs true    # then add the service
pulumi up

The service is gated behind that second flag on purpose, so the foundation can be verified before anything runs on it.

Step 3 — Domain and HTTPS

pulumi config set aitutor-aws:domain-name tutor.education.gov.xx
pulumi config set aitutor-aws:hosted-zone-id Z0123456789ABCDEFGHIJ
pulumi up

Pulumi requests the certificate, writes the validation record, waits for issuance, adds the HTTPS listener and redirects port 80. Expect it to sit waiting during validation; if it times out, nothing has changed and the site is still served on port 80.

LET THE TOOLING OWN THE VALIDATION RECORD

The certificate is re-validated on renewal using that DNS record. A hand-added record that someone later tidies up breaks the renewal about eleven months afterwards — long after anyone would connect the two events.

Step 4 — Build and deploy the application image

aws ecr get-login-password | docker login --username AWS \
  --password-stdin <acct>.dkr.ecr.<region>.amazonaws.com
docker build --platform linux/amd64 -t <ecr-url>:v1 .   # amd64 matters on Apple Silicon
docker push <ecr-url>:v1
pulumi config set aitutor-aws:image-tag v1 && pulumi up

./ops/migrate_and_seed.sh                               # one-off task

Or push to your fork's main branch and let the deploy workflow run it. Migrations must be a one-shot task here, not part of container start: the service launches every task at once, so migrations in the start command would race across replicas.

Steps 5 and 6 — Firewall, then verify

The firewall starts in count mode so you can see what it would block before it blocks anything real. Turn it on, then verify the way you would on any path:

pulumi config set aitutor-aws:waf-block-mode true && pulumi up

curl -s https://tutor.education.gov.xx/health/     # {"status": "ok", ...}

Then load the site, create a staff account, upload curriculum, and take one tutoring turn.

Path C — pip install, no Docker

The same application installed as a Python package, for an estate where containers are ruled out.

What you need first

  • A Linux server: 4 vCPU, 8 GB RAM, 60 GB disk.
  • Python 3.12 or newer — the framework version requires it.
  • PostgreSQL 14+ with the pgvector extension available. The extension is created by a migration; it only has to be available, not enabled by hand.
  • A domain pointing at the server, and something to terminate TLS.
  • Roughly 3 GB of disk for the dependencies alone.
sudo apt install python3.12 python3.12-venv postgresql postgresql-16-pgvector
sudo -u postgres createuser --pwprompt aitutor
sudo -u postgres createdb --owner aitutor aitutor

sudo python3.12 -m venv /opt/ai-tutor/venv
sudo /opt/ai-tutor/venv/bin/pip install ai-tutor

sudo /opt/ai-tutor/venv/bin/ai-tutor init      # writes /etc/ai-tutor/ai-tutor.env (0600)

init generates a signing key and creates the data directory. Re-running it never overwrites an existing file — rotating the key would log every user out and void every outstanding password-reset link. Edit that file and set ALLOWED_HOSTS, CSRF_TRUSTED_ORIGINS (with the scheme), DATABASE_URL and at least one provider key.

sudo /opt/ai-tutor/venv/bin/ai-tutor migrate
sudo /opt/ai-tutor/venv/bin/ai-tutor seed
sudo /opt/ai-tutor/venv/bin/ai-tutor collectstatic --noinput
sudo /opt/ai-tutor/venv/bin/ai-tutor createsuperuser

sudo /opt/ai-tutor/venv/bin/ai-tutor systemd | sudo tee /etc/systemd/system/ai-tutor.service
sudo systemctl daemon-reload && sudo systemctl enable --now ai-tutor

The generated unit carries this installation's real paths, restarts on failure and confines writes to the data directory. It binds 0.0.0.0:8000 with a 300-second timeout — long, because a tutoring turn takes 20 to 90 seconds and a shorter timeout kills the worker mid-answer. Whatever proxy you put in front must health-check /health/ over plain HTTP and forward X-Forwarded-Proto; /health/ is exempt from the HTTPS redirect for exactly that reason. With nginx, set proxy_read_timeout 300s; — the 60-second default cuts long replies off mid-sentence.

WHAT THIS PATH DOES NOT GIVE YOU

The database — installing, tuning, securing and backing up Postgres is yours, and nothing here creates a backup schedule. TLS — no certificate is obtained or renewed for you. Isolation — the application runs as a normal process, not in a container. And note that leaving the database URL unset falls back to a file-based database in the data directory: workable for one small school, but pgvector is unavailable there, so knowledge-base search degrades to a slower exact scan that will not hold up under a whole school.

Upgrading is manual on this path, and it is the one most often got wrong: pip replaces the code and restarts nothing.

sudo /opt/ai-tutor/venv/bin/pip install --upgrade ai-tutor
sudo /opt/ai-tutor/venv/bin/ai-tutor migrate
sudo /opt/ai-tutor/venv/bin/ai-tutor collectstatic --noinput
sudo systemctl restart ai-tutor

Symptoms first, because that is how they present.

Backup and restore

PathHow
AScripts ship alongside the compose file: ./backup.sh → ./backups/aitutor-YYYY-MM-DD-HHMM.tar.gz, and ./restore.sh backups/<file>.tar.gz to put it back. The archive holds the database and the uploaded media, taken together.
BThe managed database takes automated backups on a 14-day window; restore through the console or the shipped restore script. Media lives in object storage and is versioned separately.
CNothing is scheduled for you. Both halves, together: pg_dump -Fc aitutor > /mnt/backup/aitutor-$(date +%F).dump and tar czf /mnt/backup/media-$(date +%F).tar.gz -C /var/lib/ai-tutor media. Put both in a timer on the day you install.

The database holds the reference to every figure and the volume holds the file, which is why the two are taken together: a database restored against older media leaves lessons with broken images and reports no error.

THREE RULES THAT APPLY TO EVERY PATH

A backup that only exists on the machine it backs up is not a backup. Backups contain student records — store them encrypted, with access restricted to the same people who can reach the server. And test a restore: an untested backup is a guess, so do it once on a spare machine before you need it.
