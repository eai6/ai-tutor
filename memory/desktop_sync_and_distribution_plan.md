# Desktop ↔ cloud sync, Windows/macOS builds, public distribution — Plan (2026-08-08)

## Context

The desktop build runs fully offline: per-device SQLite, a local Ollama model,
content delivered by USB content pack. Nothing it produces ever reaches the
cloud, so a teacher's dashboard shows nothing for a class taught offline. We
want the device to keep working with no internet and reconcile with the cloud
whenever it has some.

Three things are wanted: two-way sync, Windows/macOS-only builds, and installers
colleagues can actually download.

**Decisions taken:** public S3 download page (repo stays private); student
identity comes from a roster shipped in the content pack; full two-way sync as
the destination, built in phases.

### What the audit found

- `DeviceState` (`apps/desktop/models.py:17-71`) already has `device_id` (UUID)
  and `last_sync_at`. **Both are dead** — no reference anywhere outside the model
  and its migration. The intent is on record; none of the machinery exists.
- **A DRF + JWT stack already exists** at `apps/api/`, mounted at `/api/v1/`
  (`config/urls.py:43`), with `JWTAuthentication` configured
  (`config/settings.py:475-486`), institution scoping in `apps/api/mixins.py:21-51`
  and `apps/api/permissions.py:12-20`.
- **The mobile app already has a sync endpoint** — `apps/api/views/sync.py:50-141`
  — implementing exactly the conflict policy we need: turns deduped by
  `client_uuid`, `engine_state` last-write-wins on a client timestamp, attempts
  append-only. This is the thing to extend, not to reinvent.
- Content packs exist both ways already: `build_pack()` (`apps/desktop/packs.py:113-194`)
  on the server, `import_pack()` (`:215-301`) on the device, versioned by
  `ContentPackVersion` (`apps/curriculum/models.py:897-917`) with sha256 per part
  and a `schema_rev` guard. Distribution is USB only — **no HTTP pull path**.
- **Identity is the hard problem.** Every device has its own `auth_user` table;
  students self-register (`apps/accounts/views.py:89-160`) and get device-local
  integer PKs. `StudentLessonProgress.unique_together = ['student','lesson']`
  therefore does *not* identify the same real student on two devices.
- Every syncable model uses `BigAutoField`. Two devices both mint
  `TutorSession` id=1. PKs cannot cross the boundary.
- The desktop PyInstaller spec **excludes** `boto3/anthropic/openai/azure`
  (`AI-Tutor.spec:130-131`) — "an offline build never calls them". Any sync
  client must use `requests`/`urllib`, or the exclusion list must change.

## Part B — Public download page on S3

The repo is **private**, so a GitHub Release needs a logged-in collaborator —
which does not meet "send it to people to download". Publish instead to a public
prefix on S3.

1. **New public-read bucket** `aitutor-downloads-<account>` in
   `infra/aws/components/storage.py`, deliberately separate from the media and
   ops buckets: this one is *meant* to be world-readable and must never be
   confused with the two that hold student data. Public access block off for
   this bucket only, bucket policy granting `s3:GetObject` on `public/*`.
2. **Workflow step** after packaging: upload `AI-Tutor-macos-arm64.dmg` and
   `AI-Tutor-windows-x64.zip` to `public/desktop/<tag>/`, plus copy to
   `public/desktop/latest/`.
3. **A tiny `index.html`** generated by the workflow: two download buttons, the
   version, and — critically — **the Gatekeeper/SmartScreen instructions**
   (below). Served from the same bucket.
4. **CI credentials**: the existing OIDC role is trusted for `refs/heads/*`
   (`deploy-aws.yml:13-14`). This workflow triggers on **tags**, so the role
   trust policy needs `refs/tags/desktop-v*` added or the upload will fail with
   a confusing OIDC error. Check this before the first run.

**Also add a real GitHub Release** (`softprops/action-gh-release`, and
`permissions: contents: write` — currently `contents: read` at `:47-48`) as the
internal record of what shipped. S3 is how people download; the Release is how
we know which commit produced it.

### The signing problem — flag before sending anything

Builds are unsigned and the workflow header says so (`:25-27`). macOS Gatekeeper
will refuse the DMG ("damaged and can't be opened") and Windows SmartScreen will
warn. Two honest options:

- **Now**: publish with explicit instructions (macOS: right-click → Open, or
  `xattr -d com.apple.quarantine`; Windows: More info → Run anyway). Acceptable
  for named colleagues, **not** for schools.
- **Before any pilot**: buy an Apple Developer ID ($99/yr) and a Windows code
  signing certificate (~$200-400/yr), then add `codesign`/`notarytool` and
  `signtool` steps. This is the only path that works for non-technical users.

## Part C — Two-way sync

Built in three phases so each is separately shippable and verifiable.

### Identity first (prerequisite for everything else)

Extend the content pack with a **student roster** — server user id, name,
username, grade — for the pack's institution. `build_pack()` already scopes
everything by institution (`packs.py:82-105`); add a `roster.json` part with the
same sha256 treatment.

On the device, add `server_user_id` to a local profile row and have the student
**pick their name from the roster** at first launch instead of self-registering.
Then every synced row carries a cloud-resolvable student. Keep self-registration
as a fallback for a student missing from the roster; those rows sync as
"unmatched" and a teacher reconciles them in the dashboard.

This is the piece that makes the dashboard correct. Without it, sync produces
rows that cannot be attributed to a real student.

### Phase 1 — Upload (device → cloud)

**Device side**, new `apps/desktop/sync.py` plus a `SyncOutbox` model:

```
SyncOutbox(id UUID pk, kind, payload_json, created_at,
           attempt_count, last_attempt_at, last_error)
```

Per `offline-first-expert`: a durable table, never an in-memory queue; drained by
a background thread started in `desktop_server.py` alongside the existing
first-run setup; exponential backoff **with jitter**, capped ~5 min; dead-letter
after ~5 attempts. Rows are enqueued as tutoring writes happen, so the queue
survives restarts and the UI never blocks.

Use `requests` (already a dependency) — do **not** add boto3 to the desktop
bundle.

**Cloud side**, extend `apps/api/views/sync.py` rather than writing a new
endpoint. Conflict policy per data type, matching what it already does and what
the skill prescribes:

| Data | Policy |
|---|---|
| `SessionTurn` | append-only, deduped by `client_uuid` |
| `ExitTicketAttempt` | append-only, deduped by `client_uuid` |
| `engine_state` | last-write-wins on client timestamp |
| `StudentLessonProgress` | **monotonic merge** — `max(best_score)`, never demote `mastery_level` |

**Fix the dedup properly.** Today `client_uuid` lives inside a JSONField and is
checked with a non-atomic `.exists()` (`sync.py:78-85`), so two concurrent syncs
can double-insert. Add a real indexed `client_uuid` column with a
`UniqueConstraint` on the models a device pushes, and let the database enforce
it. This is the difference between "usually idempotent" and idempotent.

**Device auth.** New server-side `Device` model (institution, device_id, name,
enrolled_at, revoked_at). Enrolment: teacher generates a short code in the
dashboard; the device posts it once with its `device_id` and receives a
long-lived refresh token; thereafter normal JWT. Revocable from the dashboard —
a lost laptop must be cuttable off.

### Phase 2 — Pull content packs over HTTP

`GET /api/v1/desktop/pack/latest/` returning the same tarball `build_pack()`
already produces, authenticated as the enrolled device and scoped to its
institution. The device compares `ContentPackVersion.version` and downloads only
when newer, verifying the existing sha256 manifest. USB import stays as the
no-internet path — this only removes the *requirement* for it.

### Phase 3 — Pull server-side changes

Roster updates and teacher overrides (e.g. a corrected `best_score`). Needs a
server-side change feed — simplest is `updated_at` watermarks per model plus
`last_sync_at` on `Device` — and the same monotonic-merge rule applied in the
device's direction. Smallest, most conflict-prone phase; do it last, when the
first two are proven in a classroom.

## Out of scope

- Code signing certificates (flagged above; a purchasing decision)
- Real-time sync — this is eventual reconciliation, batched
- Offline-created *students* being auto-provisioned as cloud accounts
- Media sync from device to cloud (figures are pack-delivered, one direction)

## Verification

- **Builds**: run the workflow with `platforms=all`; exactly two jobs run;
  the DMG opens on macOS after the documented quarantine step and the zip runs
  on Windows.
- **Distribution**: fetch both URLs with `curl` from a signed-out context
  (`aws s3 ls` is not proof — the point is anonymous access) and confirm 200.
- **Sync, the test that matters**: start the desktop app with **networking
  disabled**, complete a full lesson including the exit ticket, confirm the
  outbox has rows, then enable networking and confirm within one worker cycle
  that the session, its turns and the attempt appear in the AWS dashboard
  attributed to the right student.
- **Idempotency**: run the same sync payload twice; row counts must not change.
  Add a test asserting the `UniqueConstraint` rejects the duplicate.
- **Offline regression**: with the sync worker enabled but no network, a full
  lesson must behave exactly as it does today — no blocking, no errors surfaced
  to the student. This is the property most likely to break.
- **Revocation**: revoke the device in the dashboard; the next sync gets 401 and
  the device stops pushing without losing its queue.

## Risks

- **The desktop bundle excludes cloud SDKs by design.** Keep the sync client to
  `requests`; adding boto3 would grow the installer and contradict the build's
  stated intent.
- **Clock skew.** Last-write-wins uses client timestamps on machines that may
  never have synced a clock. Send both client time and received-at, and prefer
  the server's ordering when they disagree by more than a few minutes.
- **A device holding weeks of unsynced work** is a data-loss risk no different
  from a lost exercise book. Surface queue depth and last-sync time in the
  desktop UI so a teacher can see the device is behind.
