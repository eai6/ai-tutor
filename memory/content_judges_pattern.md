# Content Judges — Implementation Pattern (2026-05-15)

Companion to `memory/content_quality_review_plan.md`. The plan describes
what to build; this file captures the conventions that landed in Q1 so
the next content judge can be added without rediscovering them.

## Conventions (mirror these when adding a new content judge)

### 1. Cross-provider review is non-negotiable

The judge's provider must NEVER be the same provider that produced the
artefact. The chain helper enforces this via `exclude_provider`.
Rationale: same-vendor self-confirmation bias. OpenAI's judge of an
OpenAI-generated image rubber-stamps its own house style.

For the call site: pass `exclude_provider = <gen_provider>`. For
multi-stage artefacts (e.g. lesson step generated by Anthropic →
judged later), pass the originating provider on the artefact's
metadata so the judge can pick it up.

### 2. Closed violation-code enums beat free-text reasons

`PROMPT_VAGUE`, `PROMPT_HALLUCINATION_TRIGGER`, etc. are stable strings
the regen layer can pattern-match on. The model's free-text reasoning
goes in `JudgeResult.reasoning` for telemetry — but the actionable
signal is the code list. `_normalise_violations` coerces model output
into the closed set; unknown codes are dropped.

When designing a new judge: pick 4-7 codes that name CONCRETE failure
modes you've seen in real traces. Don't invent codes from first
principles.

### 3. Reason-in-prose-then-emit-JSON, with XML wrappers

Per `prompting-fundamentals-expert`: forcing strict JSON during
generation drops reasoning accuracy 10-15%. Instead: ask the model to
write `<reasoning>...</reasoning>` then `<verdict>{...}</verdict>`.
Parse the verdict tag; reasoning is best-effort. Works on every
provider — Anthropic native, Gemini and OpenAI tolerate well.

### 4. Per-judge ModelConfig purpose

Each new judge gets its own `Purpose` enum value
(`content_judge_<name>`). The `content_judge_*` prefix is consulted by
`ModelConfig.effective_temperature` to force temp 0 (verdict
consistency). Add a migration when adding a purpose.

The `_providers.py` chain falls through to
`(generation, judge, tutoring, exit_tickets)` so an unconfigured judge
still finds providers. Don't silently no-op when a purpose isn't
configured.

### 5. Fail-soft EVERYWHERE — judges never block the production path

If the judge errors, the chain is empty, or the verdict won't parse:
return `passed=True, skipped=True, skip_reason="..."`. The image
pipeline (or future content pipeline) MUST be able to proceed without
the judge. Skip reasons are surfaced to telemetry so we see the
failure mode without blocking users.

### 6. Inline consumption until ≥3 judges exist (Rule of Three)

Q1 deliberately ships ONE judge consumed inline by `image_service`
(decide-rewrite-or-proceed in 80 lines). NO orchestrator. NO regen
ensemble. The tutor-side pattern (`apps/tutoring/judges/__init__.py`
+ `apps/tutoring/validator.py` + `apps/tutoring/regen/`) is the
target shape, but ceremony before duplication is what
CLAUDE.md "Conservative bias" warns against.

When the third content judge lands (Q4 of the plan), extract:
- `apps/curriculum/content_judges/__init__.py::run_all_content_judges`
  (concurrent fan-out, mirror `run_all_judges` in tutor judges)
- A content-side `ValidationResult` with `_REGEN_ISSUES` frozenset
- `apps/curriculum/content_regen/` ensemble (cycle cap 2, temp decay
  0.20→0.15, mirror `apps/tutoring/regen/`)

### 7. PRE-gen vs POST-gen — different cost profiles

PRE-gen judges (image_prompt is the first) are cheap optimizations: ~
$0.001 text LLM call before a ~$0.04 image gen. Worth running on
every gen by default.

POST-gen judges (factual, coherence, image-vision) are quality gates:
they catch artefacts the generator already produced. Cost-equivalent
to the generation. Should be sampled or gated, not run on 100% of
generations once judge stack is full.

For now: image_prompt PRE-gen runs on every call. The four POST-gen
judges in the plan will need a sampling strategy.

## Anti-patterns to avoid

- **Free-text "verdict reasons"** — they don't compose with the regen
  layer. Use closed codes.
- **Asking the same provider that generated the artefact** —
  same-model self-confirmation bias.
- **Constrained-decoding JSON for the whole verdict** (e.g. Pydantic
  + response_schema) — kills reasoning accuracy. Use the
  reason-then-JSON wrapper instead. (When BaseLLMClient grows a
  `response_schema` argument we can revisit, but for now the wrapper
  pattern works on every provider.)
- **Blocking the production path on judge failure** — every judge
  must be skippable.
- **Skipping the prompting-skills consultation** — see
  `auto-memory/feedback_consult_prompting_skills.md`. The
  Gemini-style direct-task instruction in `image_prompt._SYSTEM_INSTRUCTION`
  came directly from the gemini-prompting-expert skill (no flowery
  "expert reviewer" persona, positive framing throughout, 4 few-shot
  examples covering the boundary cases).
